# Материализации в dbt

Материализация (*Materialization*) определяет, в каком виде dbt сохраняет результат выполнения SQL-модели в хранилище данных и что происходит с этим результатом при повторном запуске.

В dbt есть четыре основных типа материализации:

- `view`
- `table`
- `incremental`
- `ephemeral`

## 1. View

Материализация `view` создаёт SQL-представление в базе данных.

В отличие от обычной таблицы, представление не хранит собственную копию данных. Оно хранит SQL-запрос, который выполняется при обращении к представлению.

Пример модели `stg_orders.sql`:

```sql
select
    order_id,
    client_id,
    amount,
    status

from {{ source('raw', 'orders') }}
```

Конфигурация:

```sql
{{ config(materialized='view') }}
```

### Как это работает

**День 1**

В источнике `raw.orders` находится 10 записей.

Запускаем:

```bash
dbt build
```

dbt создаёт представление `stg_orders`.

При обращении к нему получаем 10 записей.

**День 2**

В источник добавили ещё 5 записей. Теперь там 15 записей.

Снова запускаем:

```bash
dbt build
```

dbt обновляет определение представления, если оно изменилось. При обращении к `stg_orders` получаем уже 15 записей.

При этом dbt не загружает и не сохраняет эти 15 записей в отдельную физическую таблицу.

**Особенности:**
- Данные физически не копируются в отдельную таблицу.
- Представление обычно занимает меньше места, чем таблица.
- При каждом обращении к представлению база данных выполняет лежащий в его основе запрос.
- Производительность зависит от сложности SQL и объёма исходных данных.

## 2. Table

Материализация `table` создаёт физическую таблицу в базе данных.

При каждом запуске dbt заново выполняет SQL-запрос модели и пересоздаёт таблицу на основе его результата.

Конфигурация:

```sql
{{ config(materialized='table') }}
```

### Как это работает

Представим, что в источнике `raw.orders` ежедневно появляются новые записи.

**День 1**

В источнике 10 записей.

Запускаем:

```bash
dbt build
```

В результате в таблице `stg_orders` находится 10 записей.

**День 2**

В источник добавили ещё 5 записей. Теперь там 15 записей.

Снова запускаем:

```bash
dbt build
```

dbt полностью пересоздаёт таблицу `stg_orders` на основе актуального результата SQL-запроса.

Теперь в ней 15 записей, а не 25.

| День | Записей в RAW | Записей в STAGING |
|---|---:|---:|
| 1 | 10 | 10 |
| 2 | 15 | 15 |
| 3 | 20 | 20 |
| 4 | 25 | 25 |

**Особенности:**
- Данные физически хранятся в таблице.
- При каждом запуске выполняется полный пересчёт модели.
- Повторный запуск не приводит к дублированию данных.
- Подходит для моделей, которые можно регулярно пересчитывать целиком.

## 3. Incremental

Материализация `incremental` позволяет обрабатывать не весь объём данных, а только новые или изменившиеся записи.

В отличие от `table`, dbt не пересоздаёт таблицу целиком при каждом запуске. Он выполняет SQL-модель и применяет результат к уже существующей таблице.

Конфигурация:

```sql
{{
    config(
        materialized='incremental',
        unique_key='order_id'
    )
}}
```

Пример модели:

```sql
select
    order_id,
    client_id,
    amount,
    status

from {{ source('raw', 'orders') }}

{% if is_incremental() %}

where order_id > (
    select max(order_id)
    from {{ this }}
)

{% endif %}
```

Здесь:
- `is_incremental()` проверяет, существует ли уже целевая таблица и выполняется ли модель в инкрементальном режиме.
- `{{ this }}` ссылается на текущую целевую таблицу модели.
- `unique_key` определяет ключ, по которому dbt может сопоставлять записи при обновлении.

### Как это работает

**День 1**

В источнике 10 записей.

Первый запуск:

```bash
dbt build
```

Поскольку таблицы ещё нет, dbt выполняет модель без условия `is_incremental()`.

В результате создаётся таблица с 10 записями.

**День 2**

В источник добавили ещё 5 записей. Теперь там 15 записей.

Снова запускаем:

```bash
dbt build
```

Условие `is_incremental()` теперь истинно.

dbt выбирает только записи, у которых `order_id` больше максимального `order_id` в существующей таблице.

В результате обрабатываются только 5 новых записей.

Теперь в целевой таблице 15 записей.

| День | Записей в RAW | Обрабатывается | Записей в целевой таблице |
|---|---:|---:|---:|
| 1 | 10 | 10 | 10 |
| 2 | 15 | 5 | 15 |
| 3 | 20 | 5 | 20 |
| 4 | 25 | 5 | 25 |

**Особенности:**
- Позволяет сократить объём повторной обработки данных.
- Требует явно определить логику отбора новых или изменившихся записей.
- `unique_key` позволяет обновлять существующие записи по ключу, если выбран соответствующий способ инкрементального обновления.
- Не гарантирует автоматическую дедупликацию входных данных.
- Необходимо учитывать поздно поступающие данные и изменения в старых записях.

Важно: приведённый пример предполагает, что `order_id` монотонно увеличивается и новые записи всегда имеют больший идентификатор. В реальных проектах часто используют дату загрузки, дату изменения записи или CDC.

## 4. Ephemeral

Материализация `ephemeral` не создаёт физическую таблицу или представление в базе данных.

Вместо этого dbt встраивает SQL такой модели непосредственно в SQL другой модели, которая на неё ссылается.

Конфигурация:

```sql
{{ config(materialized='ephemeral') }}
```

Пример модели `stg_orders.sql`:

```sql
{{ config(materialized='ephemeral') }}

select
    order_id,
    client_id,
    amount

from {{ source('raw', 'orders') }}
```

Другая модель `daily_revenue.sql`:

```sql
select
    sum(amount) as revenue

from {{ ref('stg_orders') }}
```

### Как это работает

При компиляции dbt подставляет SQL модели `stg_orders` внутрь запроса `daily_revenue`, используя CTE.

Упрощённо итоговый SQL будет выглядеть так:

```sql
with __dbt__cte__stg_orders as (

    select
        order_id,
        client_id,
        amount

    from raw.orders

)

select
    sum(amount) as revenue

from __dbt__cte__stg_orders
```

Физическая таблица `stg_orders` при этом не создаётся.

**Особенности:**
- Не создаёт физические таблицы или представления.
- SQL одной модели встраивается в SQL другой модели.
- Удобно использовать для небольших промежуточных преобразований.
- Не подходит, если результат модели необходимо независимо читать из хранилища.

## 5. Сравнение материализаций

| Материализация | Что создаётся в БД | Что происходит при повторном запуске |
|---|---|---|
| `view` | Представление | Обновляется определение SQL-представления при необходимости |
| `table` | Физическая таблица | Полный пересчёт и пересоздание таблицы |
| `incremental` | Физическая таблица | Обрабатываются выбранные новые или изменившиеся данные |
| `ephemeral` | Ничего | SQL встраивается в зависимые модели |

## 6. Какую материализацию выбрать?

Выбор зависит от объёма данных, сложности преобразований и требований к производительности.

Пример возможной архитектуры:

```text
RAW
 |
 |  Исходные данные
 |
 v
STAGING
 |
 |  view / table / incremental
 |
 v
MARTS
 |
 |  table / incremental
 |
 v
BI / Аналитика
```

Например:

| Слой | Материализация | Причина |
|---|---|---|
| RAW | Внешняя загрузка | Хранение исходных данных |
| STAGING | `view` или `incremental` | Очистка и стандартизация данных |
| MARTS | `table` или `incremental` | Подготовка аналитических витрин |
| Вспомогательные модели | `ephemeral` | Промежуточные SQL-преобразования |

Это не строгое правило: материализация выбирается отдельно для каждой модели с учётом конкретной задачи.

## 7. Как задавать материализацию в dbt?

Материализацию можно указать непосредственно в SQL-модели:

```sql
{{ config(materialized='incremental') }}
```

Или настроить через `dbt_project.yml`:

```yaml
models:
  shop:
    staging:
      +materialized: view

    marts:
      +materialized: table
```

В этом примере:
- Все модели в папке `staging` будут иметь материализацию `view`.
- Все модели в папке `marts` будут иметь материализацию `table`.

Настройка непосредственно в модели позволяет переопределить значение, заданное на уровне проекта.

## Главное, что нужно запомнить

- `view` — сохраняет SQL-представление, а не отдельную копию данных.
- `table` — каждый раз полностью пересчитывает и пересоздаёт таблицу.
- `incremental` — позволяет обрабатывать только выбранную часть данных.
- `ephemeral` — не создаёт объект в базе, а встраивает SQL в зависимые модели.

Материализация определяет, как dbt сохраняет результат модели. Сам dbt не загружает исходные данные в RAW — за это отвечает отдельный механизм загрузки данных.
